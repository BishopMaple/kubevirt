# Python Python Test Generator Skill

## Purpose

Generates **working python Python/pytest test code** from STD YAML specifications.

**Output:** Working Python test files that pass `pytest --collect-only`

**Note:** For test stubs (design review), use `python-stub-generator` instead.

**Critical:** Follows patterns from comprehensive LSP analysis of 290+ python test files.

---

## CRITICAL REQUIREMENT

**Generate ONE test function per STD scenario. No exceptions.**

- ✅ CORRECT: 8 STD scenarios → 8 generated `def test_*()` functions
- ❌ WRONG: 8 STD scenarios → 3 test files (grouped without covering all scenarios)

**Pattern-based file grouping is allowed**, but **EVERY scenario must get a test function**.

Each test function must:
- Have a unique name derived from scenario test_id
- Include scenario ID in docstring for traceability
- Implement all steps and assertions from STD scenario

---

## Input Required

- `jira_id`: Jira ticket ID (e.g., "MYPROJ-12345")

**Prerequisites:**
- STD YAML file must exist at `outputs/std/{JIRA_ID}/{JIRA_ID}_test_description.yaml`
- LSP patterns file generated by ticket-context-analyzer (fresh per-ticket)

---

## Output

**Generated Files:**
```
outputs/python-tests/{JIRA_ID}/
├── test_{feature_name}.py           (working implementation)
├── test_{another_feature}.py
├── conftest.py                       (shared fixtures)
└── ... (one file per feature group)
```

**File Characteristics:**
- **Language:** Python 3.x
- **Framework:** pytest with fixtures
- **Size:** 150-400 lines per file
- **Status:** Working code (passes pytest --collect-only)
- **Format:** Follows project-specific patterns from reference examples and LSP analysis

## Repo Rules Integration (AGENTS.md)

When `project_context.repo_rules.agents_rules` is available, apply these coding
standards from the target repository's AGENTS.md to all generated test code:

**Marker rules:**
- `python` is implicit — do NOT add `@pytest.mark.python`
- Team markers (project-specific) are implicit — do NOT add them
- `pytest.skip/skipif` are forbidden — never use in generated code

**Fixture rules (from AGENTS.md Fixture Guidelines):**
- Single responsibility — each fixture does ONE action
- NOUNS for names (`resource_with_disk`), NEVER verbs (`create_resource_with_disk`)
- `request.param` with dict structure for complex parameters
- Fixtures MUST return/yield the resource
- Ordering: pytest native → session-scoped → module/class/function scoped
- Cleanup via `yield` + cleanup code, NEVER return + finalizer

**Code patterns:**
- `conftest.py` is for fixtures only — NO helpers, utilities, or classes
- Use the project's polling utility for polling, NEVER `time.sleep()` in loops
- Use absolute imports only, NEVER relative imports
- Use `from module import func`, NEVER `import module`
- Use named arguments for function calls with more than one argument
- No single-letter variable names
- No defensive programming (fail-fast, except the 5 allowed exceptions)
- `with` for all resources (files, connections, locks)
- `raise NewError("message") from original_error` for exception context
- No `async` — the codebase does not use async/await
- Use `TYPE_CHECKING` for type-only imports
- Imports always at top of module, never inside functions

**Test structure:**
- Each test verifies ONE aspect only
- Use `@pytest.mark.usefixtures` when fixture return value is not used
- STP link required in module docstring
- Feature subdirectories required under component directory

## Workflow

### Step 1: Read STD YAML

Load `outputs/std/{JIRA_ID}/{JIRA_ID}_test_description.yaml`

**Extract:**
- Total scenario count: `len(scenarios)`
- All python scenarios (filter by `tier: "End-to-End"`)

### Step 2: Load Pattern Libraries

**Read patterns from fresh LSP analysis:**

1. **Read** `outputs/python-tests/{JIRA_ID}/{JIRA_ID}_lsp_patterns_python.yaml` (FRESH LSP analysis)
   - This file contains the LATEST patterns from actual repository code
   - Created by ticket-context-analyzer agent using LSP
   - Contains actual function signatures, imports, and usage patterns

2. **Read** `{project_context.config_dir}/patterns/python_patterns.yaml` (template selection logic)

### Step 3: Group Scenarios by Pattern

**CRITICAL: This step is for file organization only. ALL scenarios must still get test functions.**

For each scenario:
1. Detect patterns using rules from `{project_context.config_dir}/patterns/python_patterns.yaml`
2. Select template based on priority rules defined in the pattern file
3. Assign scenario to a file group

Result: Map of `{file_name: [scenario1, scenario2, ...]}`
```

### Step 4: For Each File Group

Generate the test file with ALL scenarios in the group.

**For each scenario in the group:**

1. **Detect Patterns**
   - Match scenario keywords against rules in `python_patterns.yaml`
   - Each pattern defines resource types, operations, and template mappings

2. **Generate Test Function**
   - Function name: `def test_{scenario_id_slug}():`
     - Example: `test_id: "TS-MYPROJ12345-012"` → `def test_ts_myproj12345_012_dual_stack_connectivity():`
   - Docstring: Include scenario ID for traceability
   - Test body: Implement all steps and assertions from STD scenario

3. **Collect Requirements**
   - Track imports needed for this test function
   - Track fixtures needed for this test function
   - Track markers for this test function

**After all scenarios in group processed:**

4. **Select Template** (priority-based from `{project_context.config_dir}/patterns/python_patterns.yaml`)
   - Templates are defined in `{project_context.config_dir}/templates/python/` directory
   - Each pattern in `python_patterns.yaml` maps to a template with a priority
   - The highest-priority matching pattern's template is selected
   - A default template is used if no patterns match

5. **Read Template**
   - Load selected template from `{project_context.config_dir}/templates/python/` directory
   - Reference tests are available at `{project_context.config_dir}/reference/python/`

6. **Populate File-Level Placeholders**
   - `{{JIRA_ID}}`, `{{STP_REFERENCE}}`, `{{PR_URL}}`
   - `{{FEATURE_NAME}}`, `{{feature}}`, `{{FeatureClassName}}`
   - `{{NETWORK_CONFIG_TYPE}}`, `{{NETWORK_NAME}}`, `{{NETWORK_RESOURCE_NAME}}`
   - `{{TIER}}`, `{{PRIORITY}}`, `{{POLARION_ID}}`
   - `{{TEST_FUNCTIONS}}` → ALL generated test functions from step 2
   - `{{ADDITIONAL_MARKERS}}`, `{{FIXTURES}}`

7. **Generate Imports**
   - **PRIORITY:** Use imports from `{JIRA_ID}_lsp_patterns_python.yaml` if available
   - **FALLBACK:** Use imports from `docs/python_pattern_library.yaml`
   - Follow LSP-validated import order
   - Example: `from tests.network.libs import network_utils`

8. **Generate Fixtures**
   - **PRIORITY:** Use function signatures from `{JIRA_ID}_lsp_patterns_python.yaml` if available
   - **FALLBACK:** Use signatures from `docs/python_pattern_library.yaml`
   - Class-scoped for shared resources (primary resources, network configurations)
   - Function-scoped for test-specific resources
   - **CRITICAL:** Follow fixture naming convention: `{resource}_scope_{class|function}`
   - **CRITICAL:** Use EXACT function signatures from LSP analysis (don't invent parameters)

9. **Generate Class Docstrings**
   - **MANDATORY:** Include Markers section
   - Format from LSP analysis (see patterns/pattern_rules.yaml)
   - Example:
     ```python
     """
     Tests for {feature description}.

     Markers:
         - {markers from python.yaml}

     Preconditions:
         - {shared preconditions from STD}
     """
     ```

10. **Validate Generated Code**
    - **NEW:** Verify all function calls match LSP pattern signatures
    - **NEW:** Verify all imports match LSP pattern imports
    - Context managers used for all resources
    - Readiness helpers called after resource creation (per project patterns)
    - Class docstrings include Markers section
    - No global fixture redefinition
    - **CRITICAL:** Verify number of `def test_*()` functions equals number of scenarios in group

11. **Save File**
    - Derive filename: `test_{feature_slug}.py`
    - Save to `outputs/python-tests/{JIRA_ID}/test_{feature_slug}.py`

### Step 5: Generate conftest.py (if needed)

**Generate conftest.py ONLY IF:**
- Multiple test files share fixtures
- Module-scoped fixtures needed

**DO NOT include in conftest.py:**
- Global client fixtures (already in tests/conftest.py)
- Shared authentication fixtures (already in tests/conftest.py)
- `namespace` (usually test-specific)
- Any other global fixtures from main tests/conftest.py

**Include in conftest.py:**
- Test-specific shared fixtures (class/module scope)
- Constants used across multiple test files

### Step 6: Validate Complete Coverage

**CRITICAL VALIDATION - This step is MANDATORY**

After all files generated:

1. **Count STD scenarios:**
   - Count all End-to-End scenarios in STD: `N_std`

2. **Count generated test functions:**
   - Count all `def test_*()` functions in generated files: `N_tests`

3. **Verify completeness:**
   - If `N_tests < N_std`:
     - ERROR: "Incomplete coverage - {N_std - N_tests} scenarios missing"
     - List missing scenario IDs
     - FAIL generation
   - If `N_tests == N_std`:
     - SUCCESS: "Complete coverage - all {N_std} scenarios have tests"

4. **Scenario ID mapping:**
   - For each STD scenario ID, verify it appears in test function docstrings
   - Report any missing IDs

### Step 7: Report Results

Generate summary with:
- Scenarios processed
- Python test files generated
- Conftest files generated
- Total lines of code
- Any errors or warnings

## Critical Pattern: Domain-Specific Patterns

Read domain-specific patterns (networking, storage, migration, etc.) from `{project_context.config_dir}/patterns/python_patterns.yaml`. If no project-specific patterns exist, generate test code directly from the STD scenario specifications.

Each project defines its own resource classes, fixture chains, and helper functions in its pattern files and templates.

---

## Critical Pattern: Fixture Naming

**Follow LSP convention:**
```python
# ✅ CORRECT
@pytest.fixture(scope="class")
def resource_for_migration_scope_class(namespace):
    ...

# ❌ WRONG (no scope suffix)
@pytest.fixture(scope="class")
def resource_for_migration(namespace):
    ...
```

**Pattern:** `{resource}_scope_{function|class|module|session}`

---

## Critical Pattern: Class Docstrings

**⚠️ MANDATORY:** Class docstrings MUST include Markers section.

**✅ CORRECT:**
```python
class TestFeature:
    """
    Tests for feature X.

    Markers:
        - tier1
        - p0
        - s390x

    Preconditions:
        - Running resource
    """
```

**❌ WRONG (missing Markers section):**
```python
class TestFeature:
    """
    Tests for feature X.

    Preconditions:
        - Running resource
    """
```

---

## Critical Pattern: Context Managers

**NOTE: Resource class names are project-specific. Read from `python.yaml` (`resource_classes` section).**

**✅ CORRECT:**
```python
with ResourceForTests(...) as resource:
    wait_for_ready(resource=resource)  # ✅ Call readiness helper
    yield resource
# Automatic cleanup
```

**❌ WRONG:**
```python
resource = ResourceForTests(...)
yield resource  # ❌ No context manager, no readiness call
```

---

## Critical Pattern: Module-Level Markers

**Add pytestmark at module level:**
```python
pytestmark = pytest.mark.usefixtures("namespace")

# Or multiple:
pytestmark = [
    pytest.mark.usefixtures("namespace"),
    pytest.mark.python,
]
```

## Error Handling

**If STD file not found:**
- Error + suggestion to run `/std-builder {JIRA_ID}` first
- Exit

**If LSP patterns file not found:**
- Error: "LSP patterns file not found. Run /generate-python-tests which spawns ticket-context-analyzer first."
- Exit

**If scenario pattern not recognized:**
- Warning + fallback to default template
- Continue

**If validation fails:**
- Save to `.py.invalid` file
- Show validation errors
- Continue with remaining scenarios
